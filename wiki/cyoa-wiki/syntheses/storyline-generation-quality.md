# Storyline Generation Quality

This synthesizes four `expand_frontier` eval runs made on one day (2026-09-28), tracing how output quality moved as each failure mode was fixed and naming what the [storyline eval](../runbooks/storyline-eval.md) has now shown is left to fix. Runs 1–3 ran against Qwen 3.8 27B with the Bonsai-2 ternary quantization on llama-server; run 4 ran against Gemma-4 12B (`gemma-4-12B-it-uncensored-Q4_K_M.gguf`) after the owner restarted `llama-server` on that model. Read together, the runs answer a question the project needed answered before [refinement loops](../concepts/refinement-loops.md) could be scoped with real cost/benefit numbers: what does unattended `expand_frontier` actually produce, and where does it still fail a human reader?

## The four runs

| run | model | output | budget | fix/change under test | result |
|---|---|---|---|---|---|
| 1 (`20260928-143623`) | Qwen 3.8 27B, Bonsai-2 ternary | 3 stories | `max_passages: 20, depth: 3` | none (baseline) | 7 stub/placeholder passages, 1 dots-choice, 2 lost passages, across 3 stories; 1 of 3 reached its full passage count; 2 storylines contradicted their premise |
| 2 (`20260928-152815`) | Qwen 3.8 27B, Bonsai-2 ternary | 3 stories | same budget | retries (`_ask_until`) + full-path context (`_spine`) | 0 stubs, 0 lost passages, all 3 reached 20 passages; facts held to depth 3; 0 premise contradictions; but no storyline had a real ending, and three new craft issues surfaced |
| 3 (`20260928-162631`) | Qwen 3.8 27B, Bonsai-2 ternary | 3 stories | `depth: 3, branching: 3` (no `max_passages` cap) | budget-by-shape + pacing prompts + `frontier_ending` | 0 stubs; every storyline ended (`endings == unfinished == storylines`: 7/7, 5/5, 6/6); trees came out smaller than the ceiling (10/7/8 of a possible 39); run 2's duplicate-title issue did not recur in this smaller sample |
| 4 (`20260928-191304`) | Gemma-4 12B, Q4_K_M | 3 stories | same `depth: 3, branching: 3` budget as run 3 | model swap only (no code change) | 0 stubs; every storyline ended (14/14, 16/16, 10/10); trees far larger than run 3 (21/24/17 of the same 39-passage ceiling); retries almost gone (1, 0, 0 vs. 7, 1, 8); runs 8–10× faster wall-clock (124/130/86 s vs. 1280/1206/653 s); one new failure mode: a literal `\n\n` leaked into one passage body |

Runs 1–3 kept the fix from the run before it, so that comparison is additive: run 2 isolates what retries and spine context buy over nothing, and run 3 isolates what budget-by-shape and pacing prompts buy on top of that. Run 4 holds all of that code fixed and swaps only the model, isolating what's a code-level fix (holds across models) from what's model-specific behavior (pacing, verbosity, retry rate). The runbook's History section carries the narrative detail for each run; this page is about what moving through all four says together.

## What retries actually fixed, and what they can't

Before 2026-09-28, `grow` in `backend/src/cyoa/agents.py` took the model's answer on the first try. `_ask_until` (agents.py:785) changed that: up to `MAX_ATTEMPTS = 3` calls, each retry given the reason the last one was rejected via `compose(..., error=...)`, counted on the run (`progress.retries`) and logged as a `retry` SSE event with `phase` and `reason`. The problem functions it wraps are structural, not semantic — `_blank` (agents.py:113) and `_placeholder_body` (agents.py:118) catch empty or `...`-only text, and `_fresh_choices` (agents.py:969) catches duplicate or already-existing choices. This is exactly the "validate before audit, always" principle refinement-loops leads with: these are free code checks that a model call would be wasted reproducing, and run 3's retry counts (7, 1, 8 across the three stories) show the underlying model still produces this class of junk fairly often — the fix isn't that the model stopped emitting placeholders, it's that the harness stopped accepting them.

That ceiling is the honest limit of what code-only retries buy. `_ask_until`'s `problem` callback can only detect a draft is *malformed*; it cannot tell a fluent, well-formed passage is *wrong* — narrates events out of physical order, restates the reader's choices as prose instead of offering them as choices, or reuses a sibling's title. All three of those showed up in run 2, once placeholder junk was no longer masking them, and none would trip `_blank` or `_placeholder_body`. This is precisely the gap `refine`'s model-based auditors (`audit_continuity`, `audit_choices`) are scoped to close, and run 2's findings are the first concrete evidence for what those auditors need to check for beyond the `audit_continuity`/`audit_canon` starting pair already named on that page.

## What the spine actually fixed, and its limit

`_spine` (agents.py:289) walks backward from the current passage to the story's start via the earliest inbound choice at each step (capped at `SPINE_CAP = 20`), and `gather_context` renders it as a `STORY SO FAR` block above the current passage. Before this, `grow` only saw the immediate parent, so facts set two or more passages up were invisible to the model by the time a choice needed to honor them. Run 2 confirmed the fix worked at the depth tested: fuel and oxygen readings only ever counted down across three levels in the sci-fi story, and a clue set at level 0 paid off at level 2 in the fantasy story, with no contradiction of any premise across all three stories' full storyline sets (11 + 14 + 14 = 39 storylines read).

This is worth naming precisely because it is *not* the same claim [choice anchoring](../concepts/choice-anchoring.md) makes. The spine gives the model something to read and reason about; anchoring would give the model explicit, structured world-facts each choice declares and later choices are constrained by. The spine fix is the reading half of anchoring's promise, done without a schema change — which is why refinement-loops places itself before choice-anchoring in the build order (the spine already gives `audit_continuity` something concrete to check a draft against). Anchoring remains the harder, schema-level fix for making branches *structurally* funnel toward resolution rather than merely *reading* consistently once written.

## What budget-by-shape bought, and a question it raises

Run 2's stories technically finished (all budget consumed) without a single storyline reaching a conclusion — every leaf was a mid-scene cliffhanger, because `max_passages` has no concept of "this is the last passage." The 2026-09-28 change from a flat passage cap to `depth` + `branching` (`DEFAULT_BUDGET`, agents.py:697) fixed this structurally: the last level (`left <= 1` in `grow`, agents.py:992) always writes via the `frontier_ending` role into `PassageDraft` and is flagged `is_ending`, and the `frontier_choices`/`frontier_passage` prompts were given `{branching}`/`{remaining}` placeholders so the model is told directly how much of the budget is left and instructed to narrow toward resolution as it shrinks. Run 3 confirms this at depth 3: every one of the 18 storylines read ends as a genuine resolution — the reward is claimed, the debt is paid, the light comes on — not a trailing sentence with nowhere to go.

The open question run 3 raises is why the trees came out so much smaller than the ceiling allows (10, 7, 8 passages against a possible 39). The `frontier_choices` role tells the model to "offer at most {branching} choices, and fewer when the moment holds fewer real options," and the model appears to be taking that literally — offering 2 where 3 was available in most passages sampled. That's the closure behavior working as designed, not a bug, but it means `branching` as currently phrased is a soft ceiling the model routinely doesn't reach, which matters for anyone tuning `branching` upward expecting proportionally wider trees.

## What swapping the model answered — and what it didn't

Run 4 answers the branching question a different way than proposed: instead of raising `branching`, it holds `branching: 3` fixed and swaps the model. Gemma-4 12B filled trees to 21/24/17 passages against the same 39-passage ceiling and `{branching}`/`{remaining}` prompt wording that made Qwen/Bonsai stop at 10/7/8. Since the prompt text was byte-for-byte identical, run 3's "fewer when the moment holds fewer real options" hypothesis was about model behavior, not prompt wording — some models read that instruction as license to close early, others don't. That reframes proposal 4 below: the useful experiment isn't only *raising* `branching`, it's comparing how different models respond to the *same* `branching`, which run 4 already started doing for free.

Run 4 also holds up the two claims that matter most for [refinement loops](../concepts/refinement-loops.md)' sequencing: the retry mechanism and the depth/branching closure logic are code-level guarantees that transferred cleanly across an unrelated model swap (0 stubs, 0 unfinished storylines on both models), while retry *rate* (1/0/0 vs. 7/1/8) and tree *width* are model-specific and will need to be re-measured every time the underlying model changes. That argues for keeping `--branching`/`--depth` and the retry-by-reason breakdown in every future eval run's `index.md`, even once refinement-loops lands, so a future model swap is diagnosable the way this one was.

The one new craft issue run 4 surfaced — a literal `\n\n` (the two characters, not a real line break) embedded mid-sentence in one passage body (`1-the-lighthouse-keeper-s-debt.md`, storyline 10) — is a new failure class none of runs 1–3 produced. It's not blank and it's not a `...` placeholder, so `_blank` and `_placeholder_body` (agents.py:113, 118) don't catch it; a reader sees a stray `\n\n` sitting in the middle of a sentence. At one occurrence across 40 storylines it isn't yet worth a dedicated code check, but it's evidence that a `problem` callback checking for literal backslash-escape sequences in passage/choice text would be cheap and would generalize across whichever model is loaded, unlike prose-craft issues that need a model auditor to judge.

## Proposals

1. **Feed run 2's three craft findings into R1/R2 of refinement-loops as concrete audit targets, not hypothetical ones.** The refinement-loops page already lists prose craft and pacing as "expected once R1 shows what the first three [auditors] miss" (concepts/refinement-loops.md); run 2 has already shown it, ahead of R1. Specifically: extend `audit_continuity`'s checks to cover in-passage physical/temporal sequencing (an action narrated after the character has left its location), and scope a `audit_craft` auditor (or extend `audit_choices`) to flag passage bodies that narrate the reader's remaining options as prose rather than leaving them to the choice list — both are concrete enough to write a rubric and a couple of few-shot examples from the run 2 reports directly.

2. **Treat duplicate passage titles as a code-level check, not an audit.** Unlike sequencing or prose issues, a title collision across distinct passages in the same story is mechanically detectable — a simple `SELECT title, COUNT(*) FROM passages WHERE story_id = ? GROUP BY title HAVING COUNT(*) > 1` after each `grow` batch, or folded into `_ask_until`'s `problem` check the way `_fresh_choices` already checks for duplicate choice text. This is materially cheaper than a model audit and catches the exact failure run 2 saw (three passages titled "The Willow at the Mill Race") before it ever reaches a reader. Since it didn't recur in run 3's smaller trees, this is a low-cost, high-confidence addition to make now rather than waiting to see whether it resurfaces at larger `branching`.

3. **Add a "choices offered vs. choices capped" ratio to the eval report before drawing further conclusions about `branching`.** Run 3 suggested the model was self-limiting well below the cap; run 4 showed a different model filling the same cap much more fully at the identical `branching` value, which means this ratio needs to be tracked per model, not just per budget. `index.md`'s stats table already tracks passages/storylines/endings; a column showing mean choices-per-passage against the configured `branching` would make both effects (budget tuning and model choice) visible in the same report going forward.

4. **Treat model choice as a variable in future eval comparisons, not just budget.** Run 4 showed that holding `branching: 3` fixed and swapping Qwen 3.8 27B (Bonsai-2 ternary) for Gemma-4 12B moved tree width from 10/7/8 to 21/24/17 passages and cut retries from 7/1/8 to 1/0/0 — a bigger effect on both axes than any budget change tested so far, and at roughly a tenth of the wall-clock cost. A `branching: 4`–`5` run is still worth doing (to see if the ceiling itself changes the picture), but it should be run against both models rather than assumed to generalize from one.

5. **R1 of refinement-loops should budget for a fourth comparison read**: alongside `rounds: 0` vs. the core loop, keep a *no-loop, budget-by-shape-only* storyline set (i.e. more runs like run 3 or run 4) as the control, so the eventual quality delta refinement-loops is measured against is the honest current baseline — genuinely-ending, spine-consistent, but craft-flawed stories — not the run 1/run 2 baselines that predate this session's fixes. Given run 4's speed, prefer Gemma-4 12B for this control set purely on iteration cost, but note run 4 didn't produce enough storylines yet to say whether Qwen/Bonsai's craft quality (run 2's sequencing/prose findings) or Gemma's occasional literal-`\n` leak is the more representative baseline defect to design auditors against — both should stay in scope for R1's rubric until more samples exist.

6. **Add a literal-escape-sequence check to `_ask_until`'s structural validation.** Run 4 produced one passage body with a literal `\n\n` embedded in the prose instead of a real line break — not blank, not a placeholder, so invisible to `_blank`/`_placeholder_body` (agents.py:113, 118). A `problem` callback that flags `\n`, `\t`, or similar escape sequences appearing literally in generated text (the way `_fresh_choices`, agents.py:969, already checks for duplicate choice text) would be cheap, model-agnostic, and catch this before a reader sees it — the same "cheap code check before a model audit" reasoning as proposal 2's duplicate-title check.

7. **Pacing by structure, not one countdown.** Runs 3 and 4 show that the forced ending is reliable across models, while the soft "pace toward resolution" pressure is not. They also show that passages come out short: no prompt asks for a length. [Act pacing](../concepts/act-pacing.md) (built 2026-09-29, not yet evaluated against a model) responds on both fronts. A per-story plan of acts sets branching, early-ending allowance, guidance and prose length per act. It keeps a hard-capped final Resolution level that is written long. When act pacing lands, the choices-offered ratio in proposal 3 should be reported per act.
