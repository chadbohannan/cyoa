# Backend

The backend is a single FastAPI application in `backend/`, managed by uv and run with `make backend` (which calls the `cyoa` console script in `backend/pyproject.toml`, i.e. `cyoa.main:run`, a reloading uvicorn on `127.0.0.1:${CYOA_PORT:-8765}`). It exists to own the story database and to front a local LLM for authoring assistance; the [frontend](frontend.md) is a client of it and never touches SQLite or Ollama directly.

Port 8765 rather than the conventional 8000 was chosen at bootstrap on 2026-09-19 because something else on the development machine already answered on 8000 (a Flask app returning 404s); the port is an environment variable precisely so that collision is not baked in.

## Storage

Stories live in one SQLite file, `CYOA_DB` (default `cyoa.db` in the working directory, gitignored). `cyoa/db.py` holds the schema as a single `executescript` string and creates it on app startup via a lifespan handler; there is no migration tooling, and the deliberate policy while the [story model](../concepts/story-model.md) is still moving is to delete the file to reset. `connect()` turns on `PRAGMA foreign_keys` so that deleting a story cascades to its passages, choices, and variables, and since 2026-09-19 sets `journal_mode = WAL` with a 5-second busy timeout so the background agent runs planned in [agentic authoring](../concepts/agentic-authoring.md) can write while the editor reads (the `-wal`/`-shm` sidecars are gitignored alongside `*.db`). The 2026-09-19 bootstrap interview (`20260919-bootstrap-interview.md`) chose SQLite over markdown-per-passage and a single JSON document, accepting that stories are not hand-editable or git-diffable in exchange for a queryable store the backend fully owns.

On 2026-09-19 the phase-1 schema from [the webapp UI](../concepts/webapp-ui.md) and [agentic authoring](../concepts/agentic-authoring.md) landed in one go, because there are no migrations: `stories` gained `ifid` (uuid4, upper-cased, assigned on create), `start_passage_id` (nullable FK with `ON DELETE SET NULL`, replacing `passages.is_start`) and `updated_at`; `passages` gained the world-layer columns `t`, `meta`, `reviewed` and `provenance`; and the `lore` and `events` tables were added. Any `cyoa.db` created before that change must be deleted. `db.touch_story()` bumps `updated_at`, and every write route calls it, so the Library's "last edited" is trustworthy without triggers. Phase 3 (2026-09-20) added the `proposals` table from [agentic authoring](../concepts/agentic-authoring.md): `batch` (one assist call), `verb`, `kind`, nullable `target_passage` / `target_choice` (both `ON DELETE CASCADE`, so a proposal dies with the row it was about), a JSON `payload` whose shape depends on `kind` (documented on `models.Proposal`), and `status`. Only `pending` rows travel in `StoryGraph`.

`cyoa/models.py` carries the Pydantic request/response shapes, mirroring the tables one-to-one. Each table has three shapes — `*Create` for `POST`, `*Patch` with every field optional for `PATCH`, and the full row — and the patch routes write only the fields the client actually sent (`model_dump(exclude_unset=True)`), which is what lets `null` be a legitimate value for `start_passage_id`, `t`, `to_passage` and a variable's `default`. `StoryGraph` bundles a story with all of its passages, choices, variables, lore and events, which is the one read the graph editor needs. `PlayStart`, `PlayChoose`, `PlayView` and `Problems` are the shapes of the phase-2 player and validator below.

## The evaluator

`cyoa/engine.py` is the one place the condition and effects vocabulary from [the webapp UI](../concepts/webapp-ui.md) is interpreted, landed 2026-09-20 as the first piece of phase 2. It is pure Python over plain dicts — no database access — so the player, the validator and any future export or prompt builder call the same four functions: `initial_state(variables)` seeds `{name: default}`; `check(condition, state)` evaluates a clause `{"var", "op", "value"}` or an `all`/`any` combinator, answering false for an undeclared variable, an unknown operator, a malformed shape or an uncomparable pair (a `TypeError` from ordering a bool against a string is caught, not raised); `apply(effects, state)` returns a new dict after `set`, `add`, `give` (+1) and `take` (−1, floored at zero), skipping undeclared names and non-numeric arithmetic; and `problems(start, passages, choices, variables)` runs the static checks. `condition_vars` / `effect_vars` list the names a choice mentions, which is how the validator finds undeclared variables. Booleans are deliberately excluded from "numeric" so `add` on a flag is ignored rather than turning `True` into `2`.

## Routes

All routes sit under `/api`, so the Vite dev proxy can forward one prefix. As of 2026-09-19 (phase 1) they are: `GET /api/health`; `GET/POST /api/stories`, `PATCH/DELETE /api/stories/{id}` and `GET /api/stories/{id}/graph`; a uniform `POST /api/stories/{id}/<table>` plus `PATCH/DELETE /api/stories/{id}/<table>/{row}` for each of `passages`, `choices`, `variables`, `lore` and `events`; `POST .../passages/{pid}/duplicate`; the phase-2 routes `POST .../play/start`, `POST .../play/choose` and `GET .../problems` (2026-09-20); the phase-3 routes `POST .../passages/{pid}/assist`, `POST .../proposals/{id}/accept`, `POST .../proposals/{id}/reject` and `GET /api/agents/workflows`; the phase-5 run routes `GET/POST .../runs`, `GET .../runs/{id}`, `POST .../runs/{id}/resume`, `POST .../runs/{id}/cancel`, `GET .../runs/{id}/state` and the SSE stream `GET .../runs/{id}/events`; the phase-6 tooling routes `POST .../playtest`, `GET .../export.twee`, `POST .../promote` and `POST .../passages/merge`; and `GET /api/llm/models`. The scaffold's `POST /api/llm/generate` passthrough was removed with phase 3 — nothing called it and prompts now belong to the verbs.

The five child tables share three helpers in `main.py` — `_insert`, `_update`, `_delete` — driven by a `JSON_COLS` map naming which columns are stored as JSON text (`meta`, `condition`, `effects`, `default`), so adding a table is a schema entry, three Pydantic shapes and three one-line routes. Every child write is scoped by `story_id` in the SQL, so a row id from another story answers 404 rather than leaking. `GET /api/stories` returns `StorySummary` rows (a story plus `passage_count`) ordered by `updated_at` for the Library. `POST /api/stories` also creates a "Start" passage and points `start_passage_id` at it, so a new story lands on a map that already has its entry. Cross-story references are rejected with 422: `start_passage_id` must belong to the story, and a choice's `from_passage`/`to_passage` must too. A `UNIQUE` violation (duplicate variable name) answers 409.

The player is stateless on the server, exactly as [the webapp UI](../concepts/webapp-ui.md) specifies. `play/start` takes an optional `passage_id` ("play from here"; the story's `start_passage_id` otherwise, 409 if there is none) and returns a `PlayView` — the passage, its choices in `sort_order` filtered through `engine.check`, and the initial state. `play/choose` takes `{choice_id, state}`, answers 409 if the choice is dangling or its condition fails against the submitted state (the server never trusts the client's filtering), then applies the effects and returns the next view. Before applying, the submitted state is re-keyed to the declared variables — missing names get their defaults, unknown names are dropped — so a client holding a stale state cannot invent variables. `GET .../problems` returns `no_start`, `unreachable` (passage ids not reached from the start by following non-dangling choices, ignoring conditions), `dangling` (choice ids), `undeclared` (`{choice_id, var}` pairs) and `endings` (passages with no outgoing choices), all as ids so the map can highlight them. Since phase 6 it also returns `merge_candidates`: groups of passages sharing `t`, a case-folded `meta.location` and the same `meta.events` — the same scene reached by different routes, which [agentic authoring](../concepts/agentic-authoring.md) names as the natural things to merge.

## Tooling: promotion, merging, playtest, export

Phase 6 (2026-09-20) added the tooling that makes a large agent-grown map manageable, all as thin routes over `engine.py` and the tables. `POST .../promote` takes `{root?, passage_ids?, reviewed=true}` and flips `reviewed` on the union of the explicit ids and `engine.subtree(root, …)`; the subtree is the root plus everything reachable *only* through it — passages the start or an orphan root can still reach without passing the root are excluded — which is the same rule as the map's collapse, so "Promote subtree" reviews exactly what "Collapse subtree" would hide. `POST .../passages/merge` takes `{into, passage_ids}` and folds the others into the survivor: their inbound choices are retargeted, their outgoing choices move to the survivor, a choice that thereby becomes a self-loop is dropped, the start passage moves if it was among them, and the others are deleted (the survivor keeps its own title and body; the author edits afterwards). It serves both merge candidates and endings consolidation — a crowd of stub endings selected on the map and merged into one is the consolidation. `POST .../playtest` (`{runs, max_steps, seed}`) runs `engine.random_playthroughs`, which walks the story taking a random *available* choice each step through the same `check`/`apply` as the player and returns a coverage report — `visited` counts, `unvisited` passages, `untaken` choices, `endings` reached with counts, `stuck` (choices exist but none is open in that state), `dangling` choices hit, walks `cut` by the step cap and the mean length; it is a request, not a run, because two hundred walks over a few thousand passages take milliseconds. The counters are JSON objects keyed by `str(id)`. `GET .../export.twee` renders the story through `twee.py` as Twee 3 for SugarCube: `StoryTitle`, `StoryData` with the upper-cased IFID and the start passage name, a `StoryInit` passage of `<<set $name to default>>` for the variables, then one passage per row with `reviewed`/`agent` tags and its `pos_x,pos_y` position, plain `[[Text->Target]]` links, `<<link>>` with `<<set>>` bodies for choices with effects, `<<if>>` around gated links (`==`/`!=` become `is`/`isnot`) and a `/* dangling */` comment for choices with no target; duplicate titles get ` (id)` appended because passage names are Twee's keys. The mapping is the one [interchange formats](../concepts/interchange-formats.md) laid out.

## Assist verbs and proposals

`cyoa/agents.py` holds the four targeted verbs of [the webapp UI](../concepts/webapp-ui.md) — `draft_body`, `suggest_choices`, `draft_target`, `rewrite` — as one LangGraph `StateGraph` (`gather_context → generate → parse_validate → propose`, with a conditional edge from `parse_validate` back to `generate` up to `MAX_ATTEMPTS = 3` and a `fail` sink). The verb is a field of the state, not a separate graph, because the four differ only in output schema, instruction and how the draft becomes proposal rows. `gather_context` reads the passage's neighbourhood in one transaction: story, variables, all titles (so the model can name existing targets), inbound passages with the choice text that leads here, outgoing choices, lore (capped at 20) and events at or before the passage's `t` (capped at 12, all events when `t` is null). `render_context` turns that into a labelled plain-text prompt; `INSTRUCTIONS` adds the verb's task. `generate` calls `llm.chat_model(model).with_structured_output(schema, method="json_schema")` and, on a retry, appends the previous rejection to the prompt. `parse_validate` does what a schema cannot — empty bodies, a rewrite identical to the original, suggested choices that duplicate existing ones (dropped, not rejected, unless none survive). `propose` is the only node that writes and it writes *proposals*: `edit_passage` for the two body verbs, `new_passage` bound to the dangling choice for `draft_target`, and one `new_choice` per suggestion, resolving `target_title` against existing titles case-insensitively and otherwise carrying a `new_target` stub. `run_verb` invokes the compiled graph synchronously and raises `VerbFailed` when it ends in `fail`; `workflow_json()` exposes each workflow's `get_graph().to_json()` for the future Agents view.

`canon_check` (phase 4, 2026-09-20) is the second workflow in the same module and the first autonomous one, and since the cleanup later that day it exists only as a run (the synchronous, scope-capped route that carried it before runs existed is gone — one way to do a thing): `start_canon → check_passage (one per passage, via Send) → collect`. `check_passage` reuses the verb pipeline's `gather_context` and `render_context`, asks for a `CanonReport` — a list of `{claim, conflicts_with, severity}` issues and an optional `fixed_body` — at temperature 0.2, skips passages with empty bodies, and files one `note` proposal per passage with issues (the issues in the payload, a one-line summary in `text`) plus an `edit_passage` proposal when the model offered a fix that differs from the body. Model failures are collected into `errors` per passage rather than aborting the scope. The whole run is one `batch`. After [the fan-out OOM incident](../incidents/20260920-fanout-oom.md) every model call in the module goes through `_ask`, which holds a process-wide `threading.Semaphore(MAX_CONCURRENCY)` (`CYOA_AGENT_CONCURRENCY`, default 1): the `Send` fan-out stays logical and the physical calls are a queue, across runs and verbs alike. The gate is a semaphore rather than LangGraph's `max_concurrency` because that setting sizes the executor and, at the time, deadlocked a streamed run (see the runs section), and because it would not have throttled two runs against each other. Each `check_passage` ends with `tick("checked")` on its run handle (below), which is where the dock's `n/m checked` comes from.

## Runs: expand_frontier and the run manager

Phase 5 (2026-09-20) added the third workflow and the machinery that makes any workflow a background *run*. `expand_frontier` in `agents.py` is `plan → [Send grow per frontier passage] → gather → (review | finish)`, with `review` looping back to `plan`. `plan` sets the frontier (the root at level 0, the previous level's children after that) and allots what remains of `max_passages` across it, so the budget is exact rather than approximate: a passage allotted nothing is not sent. `grow` reuses the verb prompts — `suggest_choices` for the choices out of a passage, then `draft_target` for a destination for each new one — and writes by the reviewed rule from [agentic authoring](../concepts/agentic-authoring.md): under an unreviewed parent it inserts the choice and an agent-provenance passage directly (inheriting the parent's `t`, placed a row below it) and those passages become the next frontier; under a reviewed parent it files `new_choice` proposals whose `new_target` now carries a body, and proposes nothing further. Every kept choice gets a new passage — `grow` never links to an existing title, unlike the `suggest_choices` verb — and a passage whose suggestions all duplicated its existing choices reports that in `errors`, which the manager copies into the run's `error` column at the end so a run that wrote less than asked explains itself. `gather` is the join; `after_gather` is the budget as a conditional edge — stop at `max_passages`, at `depth`, at the wall-clock `max_seconds` (a deadline fixed when the run starts, so paused time counts), when nothing new was written, or when the author said stop. `review` calls `interrupt()` between levels; the resume payload `{steer, stop}` replaces the steer text merged into every later prompt as "AUTHOR'S DIRECTION". Defaults are `DEFAULT_BUDGET = {max_passages: 12, depth: 2, max_seconds: 1800}`. `WORKFLOWS` maps a name to its uncompiled `StateGraph` builder and an input factory, which is how `canon_check` also runs as a run with no scope cap.

`runs.py` owns the lifecycle. A run is an `agent_runs` row (`workflow`, `thread_id`, `params`, `scope`, `budget`, `status`, `progress`, `error`) plus, while the process lives, an in-memory `Live` record holding its event log and worker thread. `Manager.start` builds the input, inserts the row, and launches a daemon thread that iterates `graph.stream(..., stream_mode="updates")`; `updates` chunks become `node` events (a node finished) or an `interrupt` event. Everything else a node has to say goes through an `agents.RunHandle` that the launch builds from the `Live` record and passes as `config["configurable"]["__run"]` — the double-underscore prefix (and the fact that it is not a primitive) keeps it out of checkpoint metadata, which was checked against `get_checkpoint_metadata` before relying on it. Nodes fetch it with `agents._run()` (the null handle outside a run, so the verbs pay nothing) and call `emit` for `activity` (which passage the model is working on, emitted inside `_ask` *after* the gate is acquired so queued tasks do not light up, and cleared by a `done` phase), `report(**fields)` / `tick(key)` for progress, and `check()` for cancellation. Progress is the handle's business alone: it keeps the run's cumulative dict under a lock (`Send` tasks tick concurrently — the first version lost updates), seeded from the row on resume, and emits the *whole* dict on every change, so the manager stores what arrives and the client applies what arrives; nothing downstream counts node events. That replaced a first design in which activity and progress rode LangGraph's `custom` stream and canon progress was inferred from `check_passage` node events in two places. The graph is compiled once per workflow with a sync `SqliteSaver` on `CYOA_AGENT_DB` (default `cyoa-agent.db`, `check_same_thread=False`), so the story store can be deleted without touching checkpoints, and a paused run survives a restart: the lifespan's `recover()` fails only runs that were mid-node. `resume` re-launches the thread with `Command(resume=payload)` on the same `thread_id`; `cancel` sets the `Live` record's `threading.Event`, which the handle's `check()` raises `RunCancelled` on at the next node entry or between drafts in `grow` (the stream ends as `cancelled`; a paused run is cancelled in place) — a per-run flag in place of the process-wide `agents.CANCELLED` set the first version used. `state()` exposes `get_state` values (minus the bulky context) and `get_state_history` for the Agents view. The choice of a thread and the sync saver over `AsyncSqliteSaver` is deliberate: the nodes block on Ollama, so a thread keeps the event loop free without rewriting them as coroutines. The SSE route is a polling generator over the log (`after=seq` replays), closing when the run stops running; the client reconnects on resume.

The routes in `main.py` are the human gate. `assist` validates up front (`draft_target` needs a `choice_id` that belongs to the passage and is still dangling → 422 / 404 / 409), then runs the verb in FastAPI's threadpool; `VerbFailed` is a 502 and any other failure (Ollama down, model missing) a 503. `accept` calls `_materialise`, the one function that turns a proposal kind into table rows — `edit_passage` updates the body, `new_passage` inserts with `provenance = 'agent'` and points the dangling choice at it, `new_choice` inserts the choice and, for a `new_target`, an empty agent-provenance passage first — and flips `status`; a second accept answers 409. `reject` only flips status. Discarding a batch is the client rejecting each row. `POST .../runs` validates the scope (ids of this story; exactly one for `expand_frontier`; a world to check against for `canon_check`) and answers 201 with the row while the thread runs; `resume` on a run that is not paused is 409. Proposals filed by a run carry its `run_id`, and every run row reports `pending_proposals` so the dock can offer "Review n".

## LLM

`cyoa/llm.py` builds the `ChatOllama` (`langchain-ollama`) the verbs use, at `OLLAMA_URL` with `OLLAMA_MODEL` (default `bonsai27b:latest`) as the fallback, and lists models through the `ollama` client the same package depends on. It replaced the scaffold's hand-rolled `httpx` client on 2026-09-20. Two defaults come from the phase-3 structured-output spike recorded in [agentic authoring](../concepts/agentic-authoring.md): `reasoning=False`, because qwen3.5-family models otherwise spend ~1000 "thinking" tokens per reply (138 s to say hello at ~7 tok/s on this machine; 0.8 s with reasoning off), and `method="json_schema"` for structured output, the only method that reliably returned on-schema JSON. The interview chose local Ollama over the Anthropic API; the routes turn any client failure into a 503 so an absent Ollama degrades to a clear error rather than a crash. `suggest_choices` against the seeded smoke story took ~10 s end to end.

Later on 2026-09-20 a second backend was added because the owner runs the same Bonsai 27B under `llama-server` (llama.cpp, OpenAI-compatible API on `:8080/v1`, reasoning budget 0) and it holds the GPU Ollama would need. `CYOA_LLM=openai` makes `chat_model()` return `ChatOpenAI` (`langchain-openai`) at `CYOA_OPENAI_URL` with `CYOA_OPENAI_MODEL` (llama-server ignores the name; `list_models` returns the loaded GGUF's path) and a dummy key; `make backend` defaults to this. The structured-output method is now `llm.structured_method()`, a property of the backend, because the spike had to be redone: on llama-server `json_schema` fails inside the grammar sampler (`Failed to initialize samplers`), `json_mode` leaks empty `<think>` tags that break the parser, and `function_calling` returns on-schema output in under 2 s — the opposite of the Ollama finding. Live on this backend, `canon_check` found both seeded contradictions in the smoke story with correct `conflicts_with` names, and `expand_frontier` grew a level in ~3 s per call and followed a resume steer. `_ask` in `agents.py` is the only caller, so nothing else knows which backend is loaded.

## Tests

`backend/tests/test_api.py` drives the app through FastAPI's `TestClient` against a temp-directory database (a fixture reassigns `db.DB_PATH` before the lifespan runs) and covers the story round trip with dangling-on-delete, story patching and start-passage validation, `updated_at` bumping on a child write, passage patch and duplicate, choice target validation, and the variables / lore / events CRUD, plus a play/problems scenario (hidden choice, 409 on a failed condition and on a dangling choice, play-from-here, the full `problems` shape, and 409 from `play/start` once the start passage is deleted), and three phase-6 tests: promotion by subtree stops at a passage another branch reaches and unions explicit ids; merge candidates are found across case and whitespace, and a merge retargets inbound choices, moves outgoing ones, drops the resulting self-loop and clears the candidate; and a seeded playtest reports the unreachable gated passage, dangling hits and mean length while the Twee export carries the IFID, `StoryInit`, tags, positions, deduplicated names and the macro forms. `backend/tests/test_engine.py` unit-tests the evaluator directly — clauses, combinators, the false-for-malformed rule, effect arithmetic and flooring, name collection and the reachability walk, plus `subtree` against shared and orphan-reached passages and `random_playthroughs` on a loop that opens a gate after three passes (stuck counts, unvisited, step cap, determinism by seed). `backend/tests/test_agents.py` monkeypatches `llm.chat_model` with a queue of canned outputs and exercises the verb graph end to end: the prompt carries the neighbourhood, the retry loop feeds the rejection back and gives up as a 502 after three attempts, `suggest_choices` drops duplicates and resolves titles, `draft_target` points the dangling choice on accept, `rewrite` rejects an identical body, and a proposal cascades with its passage. Two `canon_check` run tests cover the note-plus-fix output, empty-body skipping (skipped passages still tick `checked`), per-passage progress events, scope validation, the no-world 422 and per-passage error collection landing in the run's `error`; because `Send` runs checks concurrently, the fake model answers by prompt content rather than by call order. Six run tests (2026-09-20) drive `expand_frontier` through the routes with a prompt-keyed fake that names targets after their parent: level 0 writes agent passages under an unreviewed root and pauses with the expected `progress`, the SSE log has the `activity`/`done` pairs and the interrupt, resume with a steer reaches the prompts and finishes at the budget, the checkpoint is readable through `/state`; a reviewed root produces `new_choice` proposals with bodies that accept into passages; scope validation, cancel-while-paused and resume-after-cancel; cancel while the model is mid-call (the fake blocks on an `Event`; the run ends `cancelled` with no extra rows); and the workflow topologies. The `client` fixture points `runs.AGENT_DB_PATH` at the temp directory too, and a `wait` helper polls the row because the graph runs in a thread. Run with `make test-backend`; see [Running the Dev Loop](../runbooks/dev-loop.md).
