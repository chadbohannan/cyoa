# Frontend

The frontend is a Vite + React + TypeScript app in `frontend/`, started with `make frontend` on port 5173. Its `vite.config.ts` proxies `/api` to the [backend](backend.md) at `CYOA_API` (default `http://127.0.0.1:8765`), so the app code calls relative `/api/...` paths and never knows the backend's address. As of 2026-09-20 it implements phases 1 to 4 of [the webapp UI](../concepts/webapp-ui.md) and [agentic authoring](../concepts/agentic-authoring.md): the Library, the editable map with its inspector, search, problems overlay and proposal overlay, variables with clause-row editors, the Lore surface, the Player, and the assist verbs with their Accept / Reject review.

`src/api.ts` is the typed gateway: the row interfaces mirror the backend's Pydantic models field for field, and the `api` object wraps every route. The five child tables (`passages`, `choices`, `variables`, `lore`, `events`) share one `child()` factory producing `create` / `update` / `remove`, mirroring the backend's shared helpers, so the two stay in step by construction. Keeping every fetch behind this one module is what lets the [story model](../concepts/story-model.md) change shape without a hunt through components.

## State: one store per open story

`src/useStory.ts` owns the loaded `StoryGraph` for the story the shell has open. Every mutator calls the API and then patches the in-memory graph with the row the server returned — the graph is never refetched after an edit, except for `duplicatePassage`, whose copied choices are made server-side. `deletePassage` mirrors the server's cascade locally (outgoing choices vanish, inbound ones dangle, the start pointer clears). Each mutator is wrapped by `guard`, which surfaces a failed request in the shell's header instead of losing it in a promise; a failed mutator resolves to `undefined` so callers can bail. Components receive the whole store (`StoryStore`) rather than a bag of callbacks. The store also owns the assist side: `model` (the Ollama model for verbs, persisted in `localStorage` under `cyoa.model` because it is a per-browser preference, not story data), `busy` (the verb in flight, so toolbars disable and say what they are waiting on), `assist` (appends the returned proposals), `rejectProposal` / `rejectBatch` (drop locally) and `acceptProposal`, which refetches the graph because accepting may create a passage *and* a choice server-side. Canon checks are runs, so the Regenerate button on a canon note starts a one-passage `canon_check` run. Runs (phase 5) are the store's other half but live in their own hook, `src/useRuns.ts`, which `useStory` calls with `{reload, model, setError}` and spreads into the store — components still receive one `StoryStore`, and `guard` moved to `src/store.ts` so both hooks share it. `runs` is the story's `agent_runs` rows, and for every row whose status is `running` an effect opens an `EventSource` on the [backend](backend.md)'s SSE route and keeps it in a ref so re-renders do not reopen it. The stream's `onmessage` is one `switch`: `activity` events fill `activity` (passage id → phase; a `done` phase clears the entry), which the map turns into the pulsing "✍ writing…" card; `progress` events carry the run's whole progress dict and replace the row's, so the client never adds anything up; a finished `grow` or `check_passage` node means rows landed, so the graph is refetched and the map grows while the run runs; and `status` closes the stream, clears activity and refetches runs and graph. `lastNode` per run feeds the Agents view. `startRun`, `resumeRun` and `cancelRun` are thin `guard`ed calls that patch `runs` with the returned row.

## Surfaces

**Library** (`src/Library.tsx`) lists `StorySummary` cards ordered by last edit and does New / Rename / Delete with browser `prompt` / `confirm` — deliberately plain for a single-user prototype. The open story's id lives in the URL hash (`#/story/3`) so a reload lands on the same story; `App.tsx` is the router and `StoryShell` the top bar with Map / Lore / Play tabs. The shell also holds `playFrom`, the passage id that "Play from here" on the map hands to the Player; it is the Player's React `key`, so choosing a new origin remounts a fresh playthrough.

**Map** (`src/StoryCanvas.tsx`) is the React Flow canvas with a custom `passage` node type: title, first two body lines, a ▶ and accent border on the start passage, an "ending" badge on passages with no outgoing choices. Interactions: drag persists `pos_x`/`pos_y` on drag stop; double-clicking the pane creates a passage there (`zoomOnDoubleClick` is off); dragging from a card's bottom handle to another card creates a choice (`onConnect`); releasing that drag on empty canvas creates a new passage *and* a choice to it (`onConnectEnd` with `screenToFlowPosition`, which is why the canvas sits in a `ReactFlowProvider`); clicking a node or edge selects it; right-clicking a node opens a context menu with Set as start / Duplicate / Play from here / Expand from here… (selects the passage so the run dock's form targets it) / Collapse or Expand subtree / Delete. Pending proposals are drawn over the map as the plan asked: a `ghost` node type (dashed, "proposed" badge, not connectable, not draggable-to-persist) for each passage a proposal would create, a dashed accent edge for each choice it would add, and a "✎ n proposed edits" line on a card with pending body edits; clicking a ghost or dashed edge selects the proposal (`Selection` gained a `proposal` kind, and ghost ids are prefixed `g` to tell them from passage ids). A card with pending `canon_check` notes shows "⚠ n canon notes"; a card a run is working on pulses in the accent colour with "✍ writing choices…" / "writing a passage…" / "checking canon…".

**Subtree collapse** exists because a frontier run can produce far more passages than a map can draw. A collapsed passage (context menu; the set is kept per story in `localStorage` under `cyoa.collapsed.{id}`) hides every passage reachable *only* through it: `collapseSubtrees` first walks the graph from the start passage and every passage with no inbound choice without stepping past a collapsed root, and whatever that walk did not reach but the root can is hidden, along with its edges and ghosts. A passage another branch still links to therefore stays drawn, and a collapsed card shows a summary line — hidden count, depth, reviewed count, agent count — so the author can see what a run grew without drawing it.

Selection is split in two on purpose. React Flow owns which nodes are *selected* — that is what makes shift-click and shift-drag box selection work — and the canvas mirrors the selected passage ids into `scope`, which the tool strip's "Canon check (n selected)" button uses (falling back to the whole story when fewer than two are selected). Since phase 5 that button starts a `canon_check` *run* rather than calling the synchronous route, so there is no scope cap and the check shows up in the dock with its progress. The inspector's single `selection` is pushed *into* React Flow by an effect only when it changes, and graph rebuilds preserve the existing selected flags instead of recomputing them. The first version derived every node's `selected` from `selection` (and then from `scope` too) inside the node-building memo, which wiped multi-selection on every click and, once scope was folded in, re-imposed a cleared selection in a loop; a shift-click therefore also leaves `selection` alone so the effect does not collapse the set. React Flow's own Delete-key handling is disabled (`deleteKeyCode={null}`) so every deletion goes through the same confirm-when-inbound path. Nodes and edges are rebuilt from the graph and the current selection by a `useMemo`, so the store, not React Flow, is the source of truth; dangling choices are still not drawn on the canvas, but the inspector lists them in red and the problems overlay counts them on their source card. A tool strip over the canvas holds a search box, which dims every card whose title and body do not contain the query, and a Problems toggle. The toggle fetches `GET .../problems` from the [backend](backend.md) — the semantics stay server-side — and re-fetches 150 ms after every graph change while it is on; it dashes unreachable cards in red, writes "n dangling choices" on cards whose choices lack a target, dashes edges whose choice names an undeclared variable, and shows a count summary (unreachable · dangling · undeclared · endings) beside the button. Parallel edges between the same two passages overlap their labels, which is a React Flow layout limit the map does not yet work around.

**Inspector** (`src/Inspector.tsx`) is a fixed 22rem right panel keyed on the selection so drafts never leak between rows. The passage panel has title, body, a collapsed World section (`t`, `meta.location`, `meta.present`, `reviewed`, `provenance`), the ordered outgoing choices with ↑/↓ reorder (rewrites `sort_order` as the index) and a "reached from" list. The choice panel has text, a target dropdown (blank = dangling), and condition / effects as clause rows from `src/clauses.tsx`. `ConditionEditor` shows one row per `{var, op, value}` clause with an all-of / any-of selector once there are two or more; `EffectsEditor` shows one row per set / add / give / take entry. Both draw the variable dropdown from the story's table, render a flag's value as a true/false select and a stat's or item's as a number, mark an undeclared name in red, and write the whole JSON object back on every change (one clause serialises to the bare clause, none to `{}`). Shapes the rows cannot express — nested combinators, unknown keys — fall back to the raw `JsonField` with a note, and a "JSON" link on every editor opens the raw field beside the rows, so nothing an agent might write is unreachable from the UI. With nothing selected the panel shows the story: title, description, IFID, and the variables table with add / rename / re-kind / default / delete. The assist pieces live in `src/Proposals.tsx`: `AssistToolbar` under the passage body (Draft body, Suggest choices, Rewrite with a tone select; disabled while `busy`), `ProposalList` of the passage's pending proposals, and `ProposalPanel`, which shows the proposal's kind and origin, current-versus-proposed text for a body edit, the title and body of a proposed passage or the text and destination of a proposed choice, a `note`'s issues as a list with minor/major badges (and a pointer to the fix in the same batch), Accept / Reject, Regenerate (rejects the batch and re-runs the same verb, or re-checks the one passage for a canon note) and, when the batch has siblings, Discard all and a sibling list. A dangling choice's panel shows Draft target in place of "Go to target". A single-proposal verb selects its proposal straight away; a multi-proposal one leaves the passage selected with the list beneath.

**Player** (`src/Player.tsx`) is the reader view of [the webapp UI](../concepts/webapp-ui.md). It keeps a stack of `{view, via}` steps, each a `PlayView` the server returned and the choice that led there; Back pops, Restart clears and reloads from the same origin (a nonce re-runs the load effect, so the effect itself never sets state synchronously), and when the origin is not the story's start a "From the beginning" button clears `playFrom`. Choice buttons call `play/choose` with the current view's state; a 409 (dangling choice, failed condition) is shown above the passage rather than swallowed. The collapsible Debug drawer shows the live state table, the effects of the last choice taken, and the path as passage titles — clicking an earlier title truncates the stack to that point.

**Model picker** (`ModelPicker` in `App.tsx`) sits at the right of the top bar, lists `GET /api/llm/models`, and shows "no model" when Ollama is unreachable; blank means the backend's default.

**Lore** (`src/LoreView.tsx`) is two columns: lore entries grouped by kind (character, place, faction, rule) and the events timeline sorted by `t`, each row editable in place with a `reviewed` checkbox.

**Run dock** (`src/RunDock.tsx`) sits under the map in a `.map-column` beside the inspector and is collapsible from its bar. Its form starts `expand_frontier` from the single selected passage with depth, max passages and an optional direction for the writer; below it every run of the story is a row with a status badge, a progress line (`describeProgress` in `src/runs.ts`, shared with the Agents view: "n/max passages · level l/depth" or "n/N checked"), the error if any, and per status: a steer box with Resume and Stop while paused, Cancel while running or paused, "Review n proposals" (selects the run's first pending proposal in the inspector) and a "workflow" link that opens the Agents view on that run.

**Agents** (`src/AgentsView.tsx`) is the second React Flow surface [agentic authoring](../concepts/agentic-authoring.md) asks for, kept read-only and visually distinct (pill-shaped monospace `step` nodes, dashed conditional edges, nothing draggable or connectable) so it is never mistaken for the map. It fetches `GET /api/agents/workflows` once and draws the chosen topology with a small layered layout — a node's row is the longest cycle-free path from `__start__`, so loops such as `review → plan` do not push nodes downward forever. Picking a run (from the side list or the dock) switches to its workflow, highlights the node it last finished (`lastNode` from the store) and marks the nodes LangGraph reports as `next`, and shows the checkpointed state values and the step history from `GET .../runs/{id}/state`, re-read whenever the run finishes a node or changes status.

## Autosave

There is no Save button. `src/fields.tsx` provides `TextField`, `TextArea`, `NumberField` and `JsonField`, all built on one `useDraft` hook: the control keeps a local draft, saves it 600 ms after the last keystroke or on blur, flushes a pending draft when it unmounts, and re-syncs from the prop only while the draft is clean. `NumberField` treats empty as `null` (for `t`); `JsonField` shows the parse error and does not save until the text parses.

`make test-frontend` typechecks (`tsc -b`) and builds; `npx oxlint src` is clean. There is no test runner yet; the surfaces were verified by driving Chrome against a scratch database (phase 2: problems overlay counts, clause rows on a conditioned choice, a playthrough that unlocks a gated choice, the 409 on a dangling choice, play-from-here, search dimming; phase 3, against the real `bonsai27b`: a `draft_target` ghost node and its dashed edge, two `suggest_choices` dashed edges to existing passages, Accept pointing the dangling choice at the new agent-provenance passage, and a `rewrite` proposal's current/proposed panel). `clauses.tsx` was refactored on 2026-09-20 into `ClauseRow` / `EffectRowEditor` components with shared `RowProps`, after the inline version was judged the least maintainable file.
