# Frontend

The frontend is a Vite + React + TypeScript app in `frontend/`, started with `make frontend` on port 5173. Its `vite.config.ts` proxies `/api` to the [backend](backend.md) at `CYOA_API` (default `http://127.0.0.1:8765`), so the app code calls relative `/api/...` paths and never knows the backend's address. As of 2026-09-20 it implements phases 1 to 4 of [the webapp UI](../concepts/webapp-ui.md) and [agentic authoring](../concepts/agentic-authoring.md): the Library, the editable map with its inspector, search, problems overlay and proposal overlay, variables with clause-row editors, the Lore surface, the Player, and the assist verbs with their Accept / Reject review.

`src/api.ts` is the typed gateway: the row interfaces mirror the backend's Pydantic models field for field, and the `api` object wraps every route. The five child tables (`passages`, `choices`, `variables`, `lore`, `events`) share one `child()` factory producing `create` / `update` / `remove`, mirroring the backend's shared helpers, so the two stay in step by construction. Keeping every fetch behind this one module is what lets the [story model](../concepts/story-model.md) change shape without a hunt through components.

## State: one store per open story

`src/useStory.ts` owns the loaded `StoryGraph` for the story the shell has open. Every mutator calls the API and then patches the in-memory graph with the row the server returned — the graph is never refetched after an edit, except for `duplicatePassage`, whose copied choices are made server-side. `deletePassage` mirrors the server's cascade locally (outgoing choices vanish, inbound ones dangle, the start pointer clears). Each mutator is wrapped by `guard`, which surfaces a failed request in the shell's header instead of losing it in a promise; a failed mutator resolves to `undefined` so callers can bail. Components receive the whole store (`StoryStore`) rather than a bag of callbacks. The store also owns the assist side: `model` (the Ollama model for verbs, persisted in `localStorage` under `cyoa.model` because it is a per-browser preference, not story data), `busy` (the verb in flight, so toolbars disable and say what they are waiting on), `assist` (appends the returned proposals), `rejectProposal` / `rejectBatch` (drop locally) and `acceptProposal`, which refetches the graph because accepting may create a passage *and* a choice server-side. Canon checks are runs, so the Regenerate button on a canon note starts a one-passage `canon_check` run. Runs (phase 5) are the store's other half but live in their own hook, `src/useRuns.ts`, which `useStory` calls with `{reload, model, setError}` and spreads into the store — components still receive one `StoryStore`, and `guard` moved to `src/store.ts` so both hooks share it. `runs` is the story's `agent_runs` rows, and for every row whose status is `running` an effect opens an `EventSource` on the [backend](backend.md)'s SSE route and keeps it in a ref so re-renders do not reopen it. The stream's `onmessage` is one `switch`: `activity` events fill `activity` (passage id → phase; a `done` phase clears the entry), which the map turns into the pulsing "✍ writing…" card; `progress` events carry the run's whole progress dict and replace the row's, so the client never adds anything up; a finished `grow` or `check_passage` node means rows landed, so the graph is refetched and the map grows while the run runs; and `status` closes the stream, clears activity and refetches runs and graph. `startRun`, `resumeRun` and `cancelRun` are thin `guard`ed calls that patch `runs` with the returned row.

## Surfaces

**Library** (`src/Library.tsx`) lists `StorySummary` cards ordered by last edit and does New / Rename / Delete with browser `prompt` / `confirm` — deliberately plain for a single-user prototype. The open story's id lives in the URL hash (`#/story/3`) so a reload lands on the same story; `App.tsx` is the router and `StoryShell` the top bar with Map / Lore / Play tabs. The shell also holds `playFrom`, the passage id that "Play from here" on the map hands to the Player; it is the Player's React `key`, so choosing a new origin remounts a fresh playthrough.

**Map** (`src/StoryCanvas.tsx`) is the React Flow canvas with a custom `passage` node type: title, first two body lines, a ▶ and accent border on the start passage, an "ending" badge on passages with no outgoing choices. Interactions: drag persists `pos_x`/`pos_y` on drag stop; double-clicking the pane creates a passage there (`zoomOnDoubleClick` is off); dragging from a card's bottom handle to another card creates a choice (`onConnect`); releasing that drag on empty canvas creates a new passage *and* a choice to it (`onConnectEnd` with `screenToFlowPosition`, which is why the canvas sits in a `ReactFlowProvider`); clicking a node or edge selects it; right-clicking a node opens a context menu with Set as start / Duplicate / Play from here / Expand from here… (selects the passage so the run dock's form targets it) / Collapse or Expand subtree / Delete. Pending proposals are drawn over the map as the plan asked: a `ghost` node type (dashed, "proposed" badge, not connectable, not draggable-to-persist) for each passage a proposal would create, a dashed accent edge for each choice it would add, and a "✎ n proposed edits" line on a card with pending body edits; clicking a ghost or dashed edge selects the proposal (`Selection` gained a `proposal` kind, and ghost ids are prefixed `g` to tell them from passage ids). A card with pending `canon_check` notes shows "⚠ n canon notes"; a card a run is working on pulses in the accent colour with "✍ writing choices…" / "writing a passage…" / "checking canon…". A card whose `meta.audit.verdict` is `"unresolved"` (a [refinement](../concepts/refinement-loops.md) pass that gave up on it with issues still open) shows "⚠ refinement flagged this passage", read straight off `/graph`'s `meta` field rather than a separate `problems` check — `problems.flagged` (R2) will eventually gate this the way `unreachable`/`dangling` already are.

**Subtree collapse** exists because a frontier run can produce far more passages than a map can draw. A collapsed passage (context menu; the set is kept per story in `localStorage` under `cyoa.collapsed.{id}`) hides every passage reachable *only* through it: `collapseSubtrees` first walks the graph from the start passage and every passage with no inbound choice without stepping past a collapsed root, and whatever that walk did not reach but the root can is hidden, along with its edges and ghosts. A passage another branch still links to therefore stays drawn, and a collapsed card shows a summary line — hidden count, depth, reviewed count, agent count — so the author can see what a run grew without drawing it.

Selection is split in two on purpose. React Flow owns which nodes are *selected* — that is what makes shift-click and shift-drag box selection work — and the canvas mirrors the selected passage ids into `scope`, which the tool strip's "Canon check (n selected)" button uses (falling back to the whole story when fewer than two are selected). Since phase 5 that button starts a `canon_check` *run* rather than calling the synchronous route, so there is no scope cap and the check shows up in the dock with its progress. The inspector's single `selection` is pushed *into* React Flow by an effect only when it changes, and graph rebuilds preserve the existing selected flags instead of recomputing them. The first version derived every node's `selected` from `selection` (and then from `scope` too) inside the node-building memo, which wiped multi-selection on every click and, once scope was folded in, re-imposed a cleared selection in a loop; a shift-click therefore also leaves `selection` alone so the effect does not collapse the set. React Flow's own Delete-key handling is disabled (`deleteKeyCode={null}`) so every deletion goes through the same confirm-when-inbound path. Nodes and edges are rebuilt from the graph and the current selection by a `useMemo`, so the store, not React Flow, is the source of truth; dangling choices are still not drawn on the canvas, but the inspector lists them in red and the problems overlay counts them on their source card. A tool strip over the canvas holds a search box, which dims every card whose title and body do not contain the query, and a Problems toggle. The toggle fetches `GET .../problems` from the [backend](backend.md) — the semantics stay server-side — and re-fetches 150 ms after every graph change while it is on; it dashes unreachable cards in red, writes "n dangling choices" on cards whose choices lack a target, dashes edges whose choice names an undeclared variable, and shows a count summary (unreachable · dangling · undeclared · endings · merge groups) beside the button; since phase 6 cards in a merge group carry a "⧉ merge candidate ×n" line. When two or more passages are selected the strip also offers "Review n" / "Unreview n" (`POST .../promote` with the ids; the store patches `reviewed` locally from the returned ids) and "Merge n → title", which folds the selection into the inspected passage when it is one of them, else the lowest id, after a confirm; the store refetches because choices moved server-side. The context menu's "Promote subtree" / "Unreview subtree" sends the root and lets the backend pick the subtree, so it flips exactly what "Collapse subtree" hides. Parallel edges between the same two passages overlap their labels, which is a React Flow layout limit the map does not yet work around.

**Inspector** (`src/Inspector.tsx`) is a fixed 22rem right panel keyed on the selection so drafts never leak between rows. The passage panel has title, body, a collapsed World section (`t`, `meta.location`, `meta.present`, `reviewed`, `provenance`), the ordered outgoing choices with ↑/↓ reorder (rewrites `sort_order` as the index) and a "reached from" list. The choice panel has text, a target dropdown (blank = dangling), and condition / effects as clause rows from `src/clauses.tsx`. `ConditionEditor` shows one row per `{var, op, value}` clause with an all-of / any-of selector once there are two or more; `EffectsEditor` shows one row per set / add / give / take entry. Both draw the variable dropdown from the story's table, render a flag's value as a true/false select and a stat's or item's as a number, mark an undeclared name in red, and write the whole JSON object back on every change (one clause serialises to the bare clause, none to `{}`). Shapes the rows cannot express — nested combinators, unknown keys — fall back to the raw `JsonField` with a note, and a "JSON" link on every editor opens the raw field beside the rows, so nothing an agent might write is unreachable from the UI. With nothing selected the panel shows the story: title, description, IFID, and the variables table with add / rename / re-kind / default / delete. The assist pieces live in `src/Proposals.tsx`: `AssistToolbar` under the passage body (Draft body, Suggest choices, Rewrite with a tone select, and Suggest next step — enabled only when the passage has no outgoing choices yet, since it exists to decide what a frontier passage should do next; disabled while `busy`), `ProposalList` of the passage's pending proposals, and `ProposalPanel`, which shows the proposal's kind and origin, current-versus-proposed text for a body edit, the title and body of a proposed passage or the text and destination of a proposed choice, a `note`'s issues as a list with minor/major badges (and a pointer to the fix in the same batch), a `new_choice` proposal's `payload.audit` (same [refinement](../concepts/refinement-loops.md) flag as the map, rendered by the shared `AuditFlag` component both the proposal panel and the passage panel use) with its own issue list, Accept / Reject, Regenerate (rejects the batch and re-runs the same verb, or re-checks the one passage for a canon note) and, when the batch has siblings, Discard all and a sibling list. A dangling choice's panel shows Draft target in place of "Go to target". Any assist call selects its first proposal straight away, whether it returned one row or several.

Reviewing more than one proposal used to mean bouncing back out to the passage panel after every Accept, then re-entering the list — clumsy once a run or a `suggest_choices` batch left several pending at once. `ProposalPanel` (2026-09-20) now sorts every pending proposal in the story by id (creation order, which is also batch order) into a queue, and shows `‹ Prev` / `n of total pending` / `Next ›` beside Accept/Reject so a review pass can step through it without detouring through a passage. Accept and Reject are symmetric: both resolve the current proposal and land on whatever now occupies its slot in the shrunken queue — the item that was next, or the one before it if the resolved proposal was last, or the passage only once the whole queue is empty. The per-batch "Same batch" sibling list still exists underneath for jumping straight to a named choice, but the queue is the primary way through a review pass now.

**Player** (`src/Player.tsx`) is the reader view of [the webapp UI](../concepts/webapp-ui.md). It keeps a stack of `{view, via}` steps, each a `PlayView` the server returned and the choice that led there; Back pops, Restart clears and reloads from the same origin (a nonce re-runs the load effect, so the effect itself never sets state synchronously), and when the origin is not the story's start a "From the beginning" button clears `playFrom`. Choice buttons call `play/choose` with the current view's state; a 409 (dangling choice, failed condition) is shown above the passage rather than swallowed. The collapsible Debug drawer shows the live state table, the effects of the last choice taken, and the path as passage titles — clicking an earlier title truncates the stack to that point.

**Model picker** (`ModelPicker` in `App.tsx`) sits at the right of the top bar, lists `GET /api/llm/models`, and shows "no model" when Ollama is unreachable; blank means the backend's default.

**Lore** (`src/LoreView.tsx`) is two columns: lore entries grouped by kind (character, place, faction, rule) and the events timeline sorted by `t`, each row editable in place with a `reviewed` checkbox.

**Run dock** (`src/RunDock.tsx`) sits under the map in a `.map-column` beside the inspector and is collapsible from its bar. Since 2026-09-29 its form is one line: the story's [pacing plan](../concepts/act-pacing.md) summarised (`describePlan` in `src/runs.ts`: "Setup 1 · Confrontation 1 · Climax 1 → Resolution · depth 4"), which opens the Agents view, then Unattended and Run. Run sends the plan as the run's budget rather than letting the backend read the saved one, so a run copies exactly what the author sees even while an edit is still waiting to autosave. The depth, branching and steer fields it had before are gone; the steer lives on the plan's Premise. Below the form every run of the story is a row with a status badge, a progress line (`describeProgress`: "n passages · level l/depth · act name" or "n/N checked", with "· n retries", "· n audit rounds" and "· n restarts" appended when [refinement](../concepts/refinement-loops.md) reports them), the error if any, and per status: a steer box with Resume and Stop while paused, Cancel while running or paused, and "Review n proposals" (selects the run's first pending proposal in the inspector).

**Agents** (`src/AgentsView.tsx`), reworked 2026-09-29, configures how agents write and no longer watches them. [Act pacing](../concepts/act-pacing.md) describes the design and why; the mechanics are these. The *Pacing* tab has a timeline of stage buttons (Premise, each act with flex-grow equal to its levels and a tick per level, a "+" that appends an act, and Resolution) above a React Flow canvas of the per-level loop. The loop comes from `loop` in `GET /api/agents/workflows` (the backend's `FRONTIER_LOOP`), is laid out left to right by the longest cycle-free path from its first step (so `review → plan` doesn't push anything along), and draws a dashed box behind the steps that run inside `grow`. The canvas is kept visually distinct from the map (pill-shaped monospace `step` nodes, nothing draggable or connectable) so it is never mistaken for it. Selecting a stage opens its fields in the sidebar and dims the loop steps it never reaches: the ending step in an act, the passage step in the Resolution. Selecting a step opens its doc, its condition, the plan fields it reads with the selected stage's values, and a prompt panel per role it composes. A dot on a step marks an edited or unsaved role. The *Assist & canon* tab draws the verb and `canon_check` graphs the same way, from their own nodes. The runs list, the run panel and the node-highlighting that fed them (`lastNode` in `useRuns`) were removed; run provenance is the follow-on [Activity Log](../concepts/activity-log.md).

The plan is held by `src/usePacing.ts`, created per story in `StoryShell` and shared by the dock and the Agents view. It autosaves like the story's other fields: each edit applies locally at once and a `PUT` follows 500 ms after the last one, and a 422 leaves the local plan with the reason shown. The prompt panel is the same one as before (explicit Save, Revert, Reset, the default, a debounced preview for a chosen passage), except that its preview now sends the unsaved plan and the selected stage. That way the pacing slots render as that stage fills them, whether or not the autosave has landed.

Prompt roles are the one thing in the editor with an explicit Save, and the reason is their reach. An ordinary field edits one row of one story, so autosaving it is safe. A role edits every future model call in every story ([agentic authoring](../concepts/agentic-authoring.md) says why roles are global). Autosave would therefore put half-typed text in front of a verb running in another tab, and it would trip validation at every pause while a brace was only half typed. Save validates on the backend, and a 422 leaves the draft in place with the reason beside it. `src/usePrompts.ts` holds the saved list and an unsaved draft per role. `App` calls it above the story shell because roles belong to no story, so a draft survives moving between nodes, tabs and stories.

## Playtest and export

The Play tab ends with a collapsible "Random playtest" panel (`PlaytestPanel` in `Player.tsx`): a run count and one button that posts to `POST .../playtest` and renders the report as titles rather than ids — endings reached with counts, stuck passages, dangling choices hit, never-visited passages and never-taken choices — with the summary (walks, mean steps, passages seen, walks cut by the cap) in the panel head. It reads the graph from the store for titles, so a report taken right after a merge made outside the store shows the old passage count until the graph reloads. The story panel's IFID line carries an "Export Twee" download link straight to `GET .../export.twee` (`api.tweeUrl`), not a fetch, so the browser saves the file.

## Autosave

Story fields have no Save button (prompt roles in the Agents view are the one exception, explained above). `src/fields.tsx` provides `TextField`, `TextArea`, `NumberField` and `JsonField`, all built on one `useDraft` hook: the control keeps a local draft, saves it 600 ms after the last keystroke or on blur, flushes a pending draft when it unmounts, and re-syncs from the prop only while the draft is clean. `NumberField` treats empty as `null` (for `t`); `JsonField` shows the parse error and does not save until the text parses.

`make test-frontend` typechecks (`tsc -b`) and builds; `npx oxlint src` is clean. There is no test runner yet; the surfaces were verified by driving Chrome against a scratch database (phase 2: problems overlay counts, clause rows on a conditioned choice, a playthrough that unlocks a gated choice, the 409 on a dangling choice, play-from-here, search dimming; phase 3, against the real `bonsai27b`: a `draft_target` ghost node and its dashed edge, two `suggest_choices` dashed edges to existing passages, Accept pointing the dangling choice at the new agent-provenance passage, and a `rewrite` proposal's current/proposed panel). `clauses.tsx` was refactored on 2026-09-20 into `ClauseRow` / `EffectRowEditor` components with shared `RowProps`, after the inline version was judged the least maintainable file.
