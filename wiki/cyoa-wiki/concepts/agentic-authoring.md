# Agentic Authoring

This page records how LLM agents will act on the [story model](story-model.md): first as targeted verbs on a single passage, later as a fan-out that grows an exponential number of storylines, with a coherence layer that keeps every storyline true to one world. It is a design target layered on [the webapp UI](webapp-ui.md), which is built human-first; as of 2026-09-20 phases 1 to 5 of the list below are implemented — the verbs, `canon_check` and `expand_frontier` run on LangGraph, runs are checkpointed and resumable, and the map has the run dock, activity, collapse and an Agents view — while promotion tooling, merging and export (phase 6) are not. The intent comes from the owner's 2026-09-19 statement (`sources/20260919-agentic-intent.md`): targeted assistance first, then "very large numbers of agents fanning out", with storyline merging deliberately deferred and agents helping "coordinate storylines around a common baseline of world events".

The page is written in three tiers — decisions, intended direction, open questions — so that guesses are not mistaken for commitments.

## Decisions

**Two kinds of graph.** The story graph is data: passages and choices in SQLite. An agent workflow is a procedure — a LangGraph `StateGraph` — that reads that data and proposes changes to it. Passages are never LangGraph nodes. This gives the [frontend](../systems/frontend.md) two distinct React Flow surfaces (the story map and, later, an Agents view of workflow topology) that should look like one app but never be confused for each other.

**Agents touch the story only through a tool layer.** Tools wrap the [backend](../systems/backend.md): reading passages and neighborhoods, the variables table, the `problems` validator and the play evaluator that [the webapp UI](webapp-ui.md) puts in one Python module. The backend stays the sole owner of condition/effects semantics even when the caller is a model. The only mutating tools are `propose_*`, and — beyond the frontier, below — direct passage creation.

**Reviewed versus frontier.** The human gate in the webapp plan (proposals; only Accept writes) cannot survive a fan-out that produces tens of thousands of passages, and a fan-out with no gate cannot be trusted near human-authored text. The resolution is two independent facts on every passage: `reviewed` (0/1) and `provenance` (`'human'` | `'agent'`). The rule is then one sentence: *agents may write directly where `reviewed = 0`; they must propose where `reviewed = 1`.* Review becomes promotion — flipping `reviewed` on a subtree or a sample — rather than per-passage acceptance; since phase 6 that is `POST .../promote`, where a subtree is the root plus what is reachable only through it (the map's collapse rule), so a branch can be promoted without swallowing the trunk it rejoins. Lore and events carry `reviewed` too, because the world baseline is equally something an agent might extend but must not silently rewrite.

**The story clock.** Storylines are coordinated around shared *time and events*, not shared passages. Each passage may carry a story-time value `t` and, in a `meta` JSON column, its `location`, the characters `present`, and the `events` it depicts. A separate `events` table holds the world's timeline — what happens at each `t` regardless of which branch the reader took — and a `lore` table holds the bible: characters, places, factions, rules. Generation prompts include the lore and events relevant to a passage's `t`, location and cast, which is what keeps the universe consistent across branches *without* requiring branches to converge. This is why merging can be deferred: coherence comes from the clock, not from the graph's shape. `t` is a real column rather than a `meta` key because the timeline, lore slicing and any future merge-candidate search all filter on it, and SQLite cannot index inside JSON.

**Schema delta before phase 1.** Because there are no migrations, these landed on 2026-09-19 alongside `start_passage_id` and `ifid`, and the [frontend](../systems/frontend.md) already exposes `t`, `meta`, `reviewed` and the lore/events tables to the author:

```
passages  + t REAL NULL
          + meta TEXT NOT NULL DEFAULT '{}'      -- {"location", "present": [...], "events": [ids]}
          + reviewed INTEGER NOT NULL DEFAULT 0
          + provenance TEXT NOT NULL DEFAULT 'human'
lore      id, story_id, kind ('character'|'place'|'faction'|'rule'), name, body, reviewed
events    id, story_id, t REAL NOT NULL, name, body, reviewed
```

`proposals` landed with phase 3 on 2026-09-20 (shape below, under "Proposals as a table"); `agent_runs`, `proposals.run_id` and the checkpoint store landed with phase 5 the same day.

**Structured output: reasoning off, schema-constrained.** The phase-3 spike (2026-09-20, `bonsai27b` on the owner's machine) found two things every later phase depends on. First, qwen3.5-family models think by default and the thinking is the cost: "say hi in three words" took 1017 tokens and 138 s; with reasoning disabled it took 4 tokens and 0.8 s. `llm.chat_model()` therefore passes `reasoning=False`, and any future prompt that *wants* deliberation must opt in and budget for it. Second, of `with_structured_output`'s three methods, `json_schema` (Ollama's constrained decoding) returned on-schema JSON every time (6–19 s), `function_calling` worked but drifted, and `json_mode` invented fields and failed to parse. The verbs use `json_schema` on Ollama, and the `parse_validate` retry loop exists for semantic failures (empty body, identical rewrite, duplicate choices), not for JSON that does not parse. The finding is backend-specific, not general: the same model served by `llama-server` (added later that day, see the [backend](../systems/backend.md) page) rejects `json_schema` in its grammar sampler and answers `function_calling` cleanly, so the method is chosen by `llm.structured_method()` and any new backend needs its own three-method spike before it is trusted.

## Intended direction

**Targeted verbs on LangGraph.** Done 2026-09-20, after the spike above passed. The four verbs in [the webapp UI](webapp-ui.md) — draft body, suggest choices, draft target, rewrite — are one explicit graph (`gather_context → generate → parse_validate → propose`, verb as a state field) in `backend/src/cyoa/agents.py`, run synchronously, with `ChatOllama` from `langchain-ollama` having replaced the hand-rolled client in `backend/src/cyoa/llm.py`; the [backend](../systems/backend.md) page has the node-by-node detail. The tool layer is for now the graph's direct SQL reads plus `propose`; wrapping the backend's reads as LangChain tools waits for a workflow that needs a model to choose among them. Running even single-shot verbs through LangGraph is what lets them be reused as subgraphs of the fan-out and rendered in the Agents view. Workflows are *explicit* graphs with a structured-output `generate` node, not ReAct agents that pick their own tools, both because a local model's tool-calling is unproven and because an explicit graph is the only kind whose picture tells the author anything.

**Proposals as a table.** Landed 2026-09-20 as `proposals(id, story_id, batch, verb, kind, target_passage NULL, target_choice NULL, payload JSON, status, created_at)` with the six kinds `new_passage`, `new_choice`, `edit_passage`, `edit_choice`, `new_variable`, `note`; `batch` groups one assist call's output so it can be discarded or regenerated together, and a `run_id` column joins it when `agent_runs` does. Pending proposals render on the map as ghost nodes and dashed edges; the inspector shows current-versus-proposed with Accept / Reject; Accept is one backend function (`_materialise`) that turns a kind into rows and, for a `new_choice` whose target does not exist, creates the stub passage first. Sibling references are so far only that stub; a fan-out that proposes a passage *and* choices into it will need proposals to reference each other by id. Targeted verbs and autonomous runs both write here, so there is one review UI, not two.

**Runs.** Done 2026-09-20 as `agent_runs(id, story_id, workflow, thread_id UNIQUE, params, scope, budget, status, progress, error, …)` where `thread_id` is the LangGraph checkpoint key. A run is started from a map selection (`POST /stories/{id}/runs`), executed in a worker thread that streams `updates` into a per-run log served over SSE (activity, progress and the cancel flag travel on a per-run `RunHandle` the nodes find in their config, rather than on LangGraph's `custom` stream or a module-level set — a cleanup made the same day), and gated with `interrupt()` at the review node between levels; the author resumes with `Command(resume={"steer": "...", "stop": bool})`. Accepting and rejecting happen through the proposals table as before rather than in the resume payload — the plan's `accepted`/`rejected` lists turned out redundant once proposals carried a `run_id`. The `steer` text is the only conversational channel — scoped to a run, merged into every later prompt as an "AUTHOR'S DIRECTION" line — which keeps the webapp plan's "verbs, not a chat window" stance. Checkpoints live in a separate `cyoa-agent.db` (package `langgraph-checkpoint-sqlite`) so that deleting `cyoa.db` still resets the story store per [the dev loop](../runbooks/dev-loop.md) without entangling LangGraph's opaque blobs; the saver is the sync `SqliteSaver` rather than the async one planned, because the nodes block on Ollama and a thread was the smaller change. A paused run survives a restart; a run that was mid-node when the server stopped is marked failed on startup. The [backend](../systems/backend.md) page has the manager's detail.

**Workflow order.** `canon_check(scope)` first — done 2026-09-20: it walks the scoped passages, compares each to lore and events at its `t`, and files a `note` (with the issues structured in the payload) plus an `edit_passage` fix; read-mostly, cheap, high trust, and already built on `Send` with one task per passage so the fan-out shape exists before it is needed. Its first live run confirmed the sentence below the hard way — see [the fan-out OOM incident](../incidents/20260920-fanout-oom.md) — so every model call now waits on one process-wide semaphore (`CYOA_AGENT_CONCURRENCY`, default 1); LangGraph's own `max_concurrency` was tried first and dropped when it deadlocked streamed runs (the `custom` stream mode that triggered the deadlock is itself gone now, but the semaphore stays for the cross-run reason). `expand_frontier(root, depth, max_passages, max_seconds)` — done 2026-09-20 — is `plan → Send grow per frontier passage → gather → review ⟲`: `plan` allots the remaining passage budget across the frontier, `grow` reuses the verb prompts — with a note that every target must be a *new* title, since the first live run happily routed "Smell the hoard" to an unrelated existing passage and a frontier grows outward rather than looping back — and writes by the reviewed rule, and `after_gather`, a conditional edge rather than the prompt, ends the run at the passage, depth or wall-clock cap. Logically the fan-out is thousands of agents; physically it is a queue in front of one 27B model, and the budget is the real governor. `fill_dangling`, driven by the `problems` endpoint, was skipped because the `draft_target` verb and `expand_frontier` between them cover it; it can return as a run workflow if a story accumulates dangling choices faster than the author drafts them.

**UI.** All done 2026-09-20 and described on the [frontend](../systems/frontend.md) page: the proposal overlay, the activity highlight on the passage the model is working on (emitted only once its call actually starts, so a queued fan-out does not light up the whole map), multi-selection as the way to scope a run, the bottom run dock with progress against budget, Resume / Stop / Cancel and "Review N proposals", subtree collapse showing count, depth and reviewed/agent mix, and the read-only Agents tab rendering each workflow from `compiled.get_graph().to_json()`, highlighting the last finished node and the `next` nodes, and showing `get_state()` values and the `get_state_history()` step list. Pause is deliberately absent: a level is the unit of work, and the review interrupt between levels is the pause. Time-travel forks from the history remain future work.

**Phasing.** This is the one phase list for the project; [the webapp UI](webapp-ui.md) specifies the surfaces that phases 1 and 2 build. (1) Schema and storage changes listed there and above, then the editable map and inspectors, variables CRUD, and a Lore surface. (2) Evaluator, `play/start` and `play/choose`, the reader view, clause-row editors, and the `problems` endpoint with map highlighting, pulled forward because every autonomous workflow feeds on it — done 2026-09-20. (3) The structured-output spike, then targeted verbs on LangGraph, the proposals table and overlay, model picker — done 2026-09-20. (4) `canon_check` — done 2026-09-20; it began synchronous and scope-capped at 25 passages, and became run-only once runs existed. (5) `expand_frontier`, runs with checkpoints and SSE, run dock, subtree collapse, Agents view — done 2026-09-20, verified end to end against a stubbed model only. (6) Promotion tooling by subtree, merge candidates, endings consolidation, random-playthrough tester and Twee export — done 2026-09-20: `promote`, `merge_candidates` in `problems` (same `t`, location and events) with a `passages/merge` route that also consolidates a selection of stub endings into one, a seeded `playtest` coverage report over the engine, and `export.twee` for SugarCube; see the [backend](../systems/backend.md). Merging is a plain fold — the survivor keeps its text — so the "condition-gated text over the variables table" idea for papering over the merged passages' differences is still open.

## Open questions

Whether a **timeline view** (x = `t`, y = storyline lanes, events as bands) is worth a third surface is a guess; the clock makes it possible, and the map's failure to show drift between storylines is what would justify it. Whether `lore` needs subtypes beyond `kind` is unknown until the bible is written. Whether the local model (`bonsai27b` by default) catches real contradictions in `canon_check`, and whether its `expand_frontier` prose holds together across levels, was answered on 2026-09-20 once the `llama-server` backend was wired: it found both seeded contradictions (a legless Peddler strolling, sunlight in the lightless Pit) with the right lore names, and a two-level expansion followed a mid-run steer in ~3 s per call. What remains open is quality at scale — whether a frontier of hundreds of passages stays coherent — and the fix text `canon_check` offers, which on its first live run kept one contradicted claim and echoed the title into the body; the instruction now demands body-only text that repairs every listed issue, unverified live. **Merging** storylines toward a handful of endings is explicitly deferred by the owner; when it arrives, two passages sharing `t`, location and events are the natural merge candidates, and condition-gated text over the variables table is the natural way to paper over their differences.
